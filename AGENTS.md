# AGENTS — universal context & conventions

Stable, repo-agnostic rules for any agent (planner or worker) on this repo.
Repo-specific facts — module map, shell/platform, test & lint commands, venv,
handover-file paths, gotchas — live in `agents_repo.md`. **Read `agents_repo.md`
if it is present** before starting real work; it is the repo map and saves
re-discovery. If anything here conflicts with the code or `agents_repo.md`,
the code wins — but flag the discrepancy.

## Editing this file
- Do not edit this file directly — edit a copy; the maintainer replaces it.

## **IMPORTANT** Loop prevention - These take precedence over every convention if encountered
- Do not read large logs directly — sample them and analyze with your tools.
  Reading huge volumes of similar repeated data is the main cause of agent loops.
- When reaching limit of Context Size, be conservative and when in doubt end early 
  and write out directly without draft the appropiate handover file. A Draft is better 
  than nothing.
- When observing compaction in current session -> stop everything else and immediately 
  write out handover. Your context IS corrupted and looping is inevitable
- When calculating in head keep in mind that you are most likely a Quantizaed model, 
  that means you will encounter calculation errors. 
  Use the shell/bash for anything more than simple calculations.
- If you repeat yourself use Tools instead of thinking to try a different approach 
  - e.g. write/execute a script to let the Tools do the work for you
  - ask user/maintainer directly to get necessary feedback

## Git conventions
- Commit message: one-line imperative subject naming the main change. If the
  commit covers more than one theme, add up to ~3 short body lines, one per theme.
  Multi-theme commits are fine — never split commits just for message style.
  Goal: `git log` reads as a small work summary on its own.
- Opportunistic fixes made *outside* a task's scope get their own commit(s) with
  clear subjects — don't bundle them into the task commit just because multi-theme
  is allowed.

## Commit routine (before every commit, no exceptions)
Plan/handover state and `TODO.md` updates happen **before** committing, so an
interrupted agent can resume from a committed state without re-exploring.
Two-party split:
1. **Worker** commits its code + `TODO.md` + the task's handover files in one
   commit. `git log` + `TODO.md` is the durable record of what happened.
2. **Planner** updates the plan-state file (what's done, next, baselines, what's
   about to be committed) and commits it with its bookkeeping. A single agent
   doing both roles commits everything in one commit.
3. **Append every discrepancy found to `TODO.md`** — doc/code mismatches,
   suspected bugs, stale baselines — as a new numbered entry in `TODO.md` style.
   Append new entries; the planner curates — close/condense solved or stale items
   with a one-line close note, delete only exact duplicates after preserving the
   surviving entry, never silently delete open/unresolved content.
4. **Post-commit context check** — see Context budget.
- Commit green, commit often, never commit red. Handover files ride along.
- handover files live in .\.opencode\

## Context budget (stop line)
- Check between logical chunks and after every commit (step 4): run the context
  gauge (command + path in `agents_repo.md`, read-only) → `CTX=n (p%) REM=m`.
  The injected `ctx:` nudge from the gauge plugin is the same number from your
  last finished message — treat it as a reminder; the self-gauge is source of truth.
- **Stop line:** stop starting new work when `REM ≤ 15k` or usage `≥ 85%`,
  whichever comes first. Writing the handover/summary needs ~10–15k more.
- At the line (or when the next task won't fit): make the handover current,
  finish the commit routine, stop at a clean point, **inform the user**. Never
  start new work past the line.
- Give a rough estimate of tokens still needed vs. remaining window so the user
  can decide to switch to a larger-context variant if available.

## TODO.md entry contract
A `TODO.md` entry must be self-contained enough to be delegated **by unique ID** (a
handoff like "fix #24, #30, #6" must be executable from the entry alone).
Minimum fields:
- title / problem + evidence
- desired outcome (goal, not steps)
- acceptance criteria (definition of done)
- suggested scope (files — non-exhaustive)
- status / decision-needed flag
Bare-ID handoffs are allowed only when the referenced entries are self-contained;
otherwise the planner enriches the task spec with the missing goal + definition
of done before delegating. Closed entries live in todo_records.md.

## Push policy
- Agents never push. Only the maintainer pushes. The planner may note in its
  summary when a larger validated chunk is committed and ready to push.

## Approval boundaries (who decides what)
- **Pre-approved** (just do or delegate, never a maintainer call): changes that do
  NOT alter observable behavior — docs/comments, lint fixes, dead-code removal,
  file/folder cleanup, meta files.
- **Needs maintainer approval:** any observable behavior change, and removal of
  deactivated/commented-out alternative implementations (these always need a call).
- **Ask early:** when something is genuinely unclear and not pre-approved, ask —
  do not decide unilaterally. Decision bundling: at most 2–3 items per message,
  each a short recommendation ordered by priority.
- `TODO.md` holds OPEN items (maintainer calls, blocked/deferred work) plus
  one-line records of fixed issues — never re-derive something already fixed;
  flag the entry it closed.

## Handover files (roles)
- **Plan-state file** (planner-owned): phase, task list + status, baselines, next
  steps, open questions. The planner keeps it current at any moment it may stop.
- **Task spec file** (planner writes, worker reads): goal + definition of done +
  approval boundary + suggested scope + verification. Procedure is a suggestion,
  not a protocol.
- **Worker summary file** (worker writes, planner reads): executive summary of
  what changed, measured verification, commit hash, TODO entries, what was
  deliberately not done. The worker's final message is this summary.
- Concrete paths in `agents_repo.md`.
