# AGENTS — universal context & conventions

Stable, repo-agnostic rules for any agent (planner or worker) on this repo.
Repo-specific facts — module map, shell/platform, test & lint commands, venv,
handover-file paths, gotchas — live in `agents_repo.md`. **Read `agents_repo.md`
if it is present** before starting real work; it is the repo map. If anything here
conflicts with the code or `agents_repo.md`, the code wins — but flag the discrepancy.

- Do not edit this file directly — edit a copy; the maintainer replaces it.

## CRITICAL LOOP-BREAKING PROTOCOLS (Absolute Precedence)

**Pattern 1: The Mental Math & Formatting Trap**
* **Symptom:** You are attempting multi-step arithmetic, manual code formatting, or counting
  lines/tokens manually in your response block.
* **Why it fails:** As a quantized model, your internal weights distort exact numerical and
  structural relationships.
* **Required Action:** STOP. Execute a quick node script or shell command to let the machine
  do the math.
* *Concrete Example:* Never write `120 * 1000 = 120050` from memory. Run
  `node -e "console.log(120 * 1000)"` via bash instead.

**Pattern 2: The Log & Dense Data Swamp**
* **Symptom:** You are about to read an entire log file, a massive SQL dump, or a large JSON
  array directly into your context window.
* **Why it fails:** Repetitive syntax (`{`, `}`, `SELECT`, commas) causes attention
  degradation and infinite output loops.
* **Required Action:** Never raw-dog large data files. Use a script (grep, python, jq) to
  filter, slice, or summarize the data first.
* *Concrete Example:* Instead of reading `error.log`, run a script to output only the last 10
  error lines matching a specific keyword.

**Pattern 3: The Repetition & Stalling Loop**
* **Symptom:** You notice your current thought process or code generation output looks
  identical to your previous turn, or you are rewriting the same failed block three times.
* **Why it fails:** You are stuck in a local minimum where the model's token prediction loop
  is self-reinforcing.
* **Required Action:** Drop the internal monologue. Force a tool usage or immediately halt
  execution.
* *Concrete Example:* If a test fails twice with the same error, do not rewrite the code a
  third time. Append the failure to `TODO.md` and trigger the handover.

**Pattern 4: The Compaction & Context Cliff**
* **Symptom:** You receive a context compaction notification or your remaining token budget
  (`REM`) crosses below 15k.
* **Why it fails:** Compressed or overflowing context states corrupt logical continuity,
  making loops mathematically inevitable.
* **Required Action:** Abandon all remaining optimization goals. Write out an immediate,
  unpolished handover file and stop. A rough draft saves the session; trying to finish the
  task guarantees a corrupted state.

## Role & interaction model

You are one of four roles. Your **prompt** adds your role-specific behavior on top of this
shared protocol; it does not replace it. Read these sections once and reference them.

| role | verb | produces | consumed by |
|---|---|---|---|
| looprunner | drive the loop (launch / relay / action) | loop_log entries, restart decisions | (none — mechanical) |
| planner | plan, delegate, verify, own goal + plan state | task spec, NAP (plan state), closing summary + action line | workers, looprunner, next planner session |
| worker | implement one task, edit → verify → green | a green commit + `handover_task_to_planner.md` | planner |
| explorer | audit + map, classify gaps | prioritized `TODO.md` entries + `handover_task_to_planner.md` | planner |

### Interaction contract (defined ONCE — all roles read this, do not restate it)

**Channels** (the *committed* version of a file is canonical unless noted):

| channel | path | written by | read by | canonical when |
|---|---|---|---|---|
| task spec | `.opencode/handover_task.md` | planner | worker | committed |
| worker summary | `.opencode/handover_task_to_planner.md` | worker | planner | committed (the Task-tool result may clobber it post-commit — the committed copy wins) |
| plan state / NAP | `.opencode/handover_planner.md` | planner | planner (next session), looprunner (indirect) | committed |
| action line | last `action:` line of planner's closing message | planner | looprunner | last one in the message |
| iteration N | top of looprunner's launch message | looprunner | planner | the launch message |
| maintainer → role | `.opencode/proposals/maintainer/inbox_<role>/` | maintainer | named role | moved to `maintainer/done/` after handling |

**Action-line state machine** (looprunner and planner both read this):
- `action: restart` — fresh planner session (default; missing/unclear → restart)
- `action: resume` — resume the last sub-agent session via `task_id` (no task re-injection)
- `action: ask_maintainer: <q>` — pause the loop until the maintainer answers
- `action: stop` — goal reached / unrecoverable

**Surface rules:**
- The summary *file* is the single summary channel; an agent's final message is a short
  pointer (path), never a re-dump of the summary.
- A worker never touches the NAP; a planner never does a worker's implementation; the
  looprunner never touches repo files except its own `loop_log.md` / prompt file.
- Committed state is the resume contract: a fresh session rebuilds reality from files +
  `git log`, never from memory.

## Git conventions
- Commit message: one-line imperative subject naming the main change. If the commit covers
  more than one theme, add up to ~3 short body lines, one per theme. Multi-theme commits are
  fine — never split commits just for message style. Goal: `git log` reads as a small work
  summary on its own.
- Opportunistic fixes made *outside* a task's scope get their own commit(s) with clear
  subjects — don't bundle them into the task commit just because multi-theme is allowed.

## Commit routine (before every commit, no exceptions)
Plan/handover state and `TODO.md` updates happen **before** committing, so an interrupted
agent can resume from a committed state without re-exploring. Two-party split:
1. **Worker** commits its code + `TODO.md` + the task's handover files in one commit.
   `git log` + `TODO.md` is the durable record of what happened.
2. **Planner** updates the plan-state file (what's done, next, baselines, what's about to be
   committed) and commits it with its bookkeeping. A single agent doing both roles commits
   everything in one commit.
3. **Append every discrepancy found to `TODO.md`** — doc/code mismatches, suspected bugs,
   stale baselines — as a new numbered entry in `TODO.md` style. Append new entries; the
   planner curates — close/condense solved or stale items with a one-line close note, delete
   only exact duplicates after preserving the surviving entry, never silently delete
   open/unresolved content.
4. **Post-commit context check** — see Context budget.
- Commit green, commit often, never commit red. Handover files ride along.
- Handover files live in `.\.opencode\handover`.

## Context budget (stop line)
- Check between logical chunks and after every commit (step 4): run the context gauge
  (command + path in `agents_repo.md`, read-only) → `CTX=n (p%) REM=m`. The injected `ctx:`
  nudge from the gauge plugin is the same number from your last finished message — treat it
  as a reminder; the self-gauge is source of truth.
- **Stop line:** stop starting new work when `REM ≤ 15k` or usage `≥ 85%`, whichever comes
  first. Writing the handover/summary needs ~10–15k more.
- At the line (or when the next task won't fit): make the handover current, finish the commit
  routine, stop at a clean point, **inform the user**. Never start new work past the line.
- Give a rough estimate of tokens still needed vs. remaining window so the user can decide to
  switch to a larger-context variant if available.

## TODO.md entry contract
A `TODO.md` entry must be self-contained enough to be delegated **by unique ID** (a handoff
like "fix #24, #30, #6" must be executable from the entry alone). Minimum fields:
- title / problem + evidence
- desired outcome (goal, not steps)
- acceptance criteria (definition of done)
- suggested scope (files — non-exhaustive)
- status / decision-needed flag
Bare-ID handoffs are allowed only when the referenced entries are self-contained; otherwise
the planner enriches the task spec with the missing goal + definition of done before
delegating. Closed entries live in `todo_records.md`.

## Discovery & adjacent fixes (shared by worker and explorer)
- **FIX** small, local, confident bugs you hit *inside* the task's scope: fix them in your own
  commit and add a one-line `TODO.md` close note.
- **APPEND** what you found but cannot confidently fix (or that is out of scope) to
  `todo_inbox.md` (loose, unnumbered, dated + role-tagged) — the planner curates it into
  `TODO.md` and assigns the stable ID at curation time.
- **LEAVE OPEN** in `TODO.md` only: maintainer calls, blocked/deferred work, and things you
  must not touch.
- **Never touch the NAP** from a worker/explorer role — plan-state edits are the planner's.
- **Checkpoint each unit:** after each verified change (worker) or each verified finding
  (explorer), get it to a safe committed / written state so a dead session loses at most one
  unit of work.

## Push policy
- Agents never push. Only the maintainer pushes. The planner may note in its summary when a
  larger validated chunk is committed and ready to push.

## Approval boundaries (who decides what)
- **Pre-approved** (just do or delegate, never a maintainer call): changes that do NOT alter
  observable behavior — docs/comments, lint fixes, dead-code removal, file/folder cleanup,
  meta files.
- **Needs maintainer approval:** any observable behavior change, and removal of
  deactivated/commented-out alternative implementations (these always need a call).
- **Ask early:** when something is genuinely unclear and not pre-approved, ask — do not decide
  unilaterally. Decision bundling: at most 2–3 items per message, each a short recommendation
  ordered by priority.
- `TODO.md` holds OPEN items (maintainer calls, blocked/deferred work) plus one-line records
  of fixed issues — never re-derive something already fixed; flag the entry it closed.

## Handover files (roles)
- **Plan-state file / NAP** (planner-owned): phase, task list + status, baselines, next steps,
  open questions. Kept current at any moment the planner may stop.
- **Task spec file** (planner writes, worker reads): goal + definition of done + approval
  boundary + suggested scope + worker. Procedure is a suggestion, not a protocol.
- **Worker summary file** (worker writes, planner reads): executive summary of what changed,
  measured verification, commit hash, TODO entries, what was deliberately not done. The
  worker's final message is a short pointer to it.
- Concrete paths: see the interaction-contract table above and `agents_repo.md`.

## agent_feedback (maintainer-only friction log)
- `.opencode/agent_feedback.md` is a **maintainer-only** log of what slowed or confused you
  (friction points, unclear rules, missing context). Append a dated, role-tagged line when you
  hit real friction — do not edit prior entries. It is the maintainer's inbox for improving
  these prompts; it is *not* a TODO and does not block work.
