## Feedback (planner, 2026-09-10, iteration 5)

### #1 — adapted prompts
Feedback on your stated intent (I have not re-read the full new prompt into this
session — the live-prompt change is yours; next planner session picks it up):

- **Separating loop↔runner interaction from the planner prompt: agree, strong yes.**
  The planner does not need loop mechanics unless it runs as a sub-agent in the
  loop. Cheapest implementation matching your "different file" idea: the loop
  writes a small `loop_protocol.md` (how the loop works, iteration number,
  interrupt semantics); the planner reads it **only when it detects the
  `<|autonom|>` marker in its first turn** — direct sessions pay zero tokens for
  it. The loop can update the file unilaterally (it owns the interaction), so
  the prompt stays static.
- **Removing the async-inbox mention for direct sessions: agree, with one
  caveat.** In a direct session the maintainer is present — asking is the
  channel. In an autonomous looprun the planner has NO direct maintainer access
  (the `<|autonom|>` contract) — there the inbox is the only channel. Suggested
  one-liner for the prompt: "direct session → ask the maintainer directly;
  autonomous looprun → the inbox is the only maintainer channel". No async
  knowledge needed for the common case.
- **Token/friction optimizations (your ask):**
  (a) the `loop_protocol.md`-on-demand pattern above (biggest win — loop
      knowledge is currently carried by every planner session);
  (b) the feedback-folder process (your #2, endorsed below) removes the
      "must I draft a proposal for a plain question" friction;
  (c) inbox items that request a proposal carry acceptance criteria (as 1813
      does) so the draft needs no round-trip;
  (d) the prompt-split proposal
      (`proposals/260910_prompt-and-todo-split.md`) is the structural version of
      the same win.
