## Evidence (measured this session)

1. **Manual identity bookkeeping:** every call requires the agent to hand-copy
   two fields from its own injected context — the session id (from the `ctx:`
   line) and the model id (verbatim from launch context). Two error-prone
   transcription steps per call, on a line the tool already formats for the
   agent.
2. **No write confirmation / no created-vs-existing signal:** the return is
   `folder: <name>` + `line: <exact>`. When `.opencode/loop/` was empty, the
   call **created a brand-new looprun folder** — and the return did not say so.
   Observed afterward: `git status` showed `?? .opencode/loop/` (untracked);
   the previous loop folder had been archived deliberately. The agent only
   noticed on manual inspection.
3. **Cryptic 8-char status tokens:** the schema is an exact enum
   (`-->START`, `DONE<---`, `-RETURN-`, `-WARNING`, `--INFO--`); the tool
   description lists the tokens without semantics, and a near-miss spelling
   fails at parse time with a raw zod enum error.
4. **No way to annotate a wrong line:** append-only is intentional (maintainer
   confirmed the inability to correct is by design) — but there is no positive
   status for "the previous line needs a clarification/addition."

## Design

Four independently-approvable parts; build order A → B → C → D (each a task
spec written against the just-verified state).

### Part A — auto-identity (session / agent / model from the host context)

**Change:** make `session` and `model` args OPTIONAL with a context-first
resolution chain (mirroring the proven `compact_memory` v2 multi-source
pattern, `compact_memory.ts` L182/L131). Note: the `get_context_keys` probe
(2026-09-12) CONFIRMED the tool context has NO `client` key (contextKeys:
sessionID, abort, messageID, callID, extra, agent, messages, metadata, ask,
directory, worktree — no model field either) — all identity retrieval goes
through DIRECT context fields; no client-mediated path is possible:

- **session:** `args.session` → `context.sessionID` → `context.sessionId` →
  `context.session?.id` → literal `unknown`. (Order per the maintainer's
  `session_info` probe tool — added 2026-09-12 specifically to inspect the
  host context: it returns `sessionID` (camelCase, capital ID) live.)
- **model / agent identifier:** `args.model` → `context.modelId` →
  `context.model.id` → **agent identifier if the host wires one** → literal
  `unknown`.
- **Agent identifier preference (maintainer's point):** the line's
  model field carries the agent's **identifier** (e.g. `planner_Q4_120K`)
  WHEN easily available in the context, and the raw model id only as the
  fallback — the identifier is shorter and disambiguates quant variants.
  The candidate field `context.agent` is **evidence-backed**: the
  maintainer's `session_info` probe tool (2026-09-12) returns the agent
  identifier (`planner_Q4_120K`) straight from the host context. Part A's
  task spec still includes a one-time **context key dump** (e.g. into
  `.opencode/temp/ctx.log`) to confirm the custom tool's own `context`
  object exposes the same fields (the probe tool's and the custom tool's
  contexts may differ) and to close the model-field question. All fields
  stay best-effort: absent → next source → arg → `unknown`; never throw.
- `role` stays agent-provided (it is the loop role token — `planner-10`,
  `worker-13`, `looprunner` — which the host does not know); optionally it may
  be omitted and default to the agent identifier / `unknown` (Part A detail,
  planner picks at spec time).
- The **line format is unchanged**:
  `<stamp> <status> <role> <session|unknown> <model|agent|unknown> <content>`
  — existing loop-log lines and any consumer stay parseable.

### Part B — write confirmation in the return

**Change:** after `appendFileSync`, the tool **reads the file back and
byte-compares the last line** against the line it wrote. The return becomes:

```
folder: autorun-<date> (created)          <- or (existing)
line: <exact line written>
verified: readback-match                  <- or readback-MISMATCH: <last line>
```

- `(created)` vs `(existing)` — the tool flags when THIS call created the
  looprun folder (the friction in Evidence #2): the agent then knows it
  started a new looprun (which per protocol is planner work) instead of
  discovering it via `git status`.
- `verified: readback-match` — the write actually landed (the
  append-then-re-read is cheap for a small log file; on mismatch the return
  surfaces the file's actual last line so the discrepancy is visible, not
  silent).

### Part C — lenient status (formatting moves into the tool)

**Change:** `status` becomes a **free-form string**; the tool normalizes it
into the five established 8-char tokens (line format unchanged, so consumers
and the role-prompt fallback descriptions stay valid):

1. lowercase + strip everything non-alphanumeric (so `DONE`, `-DONE`,
   `-->DONE`, `done<---`, `  Done ` all normalize to `done`);
2. keyword map, checked in this order (no keyword is a substring of another,
   so order only matters for the intended `restart` → START case):
   - contains `done`   → `DONE<---`
   - contains `return` → `-RETURN-`
   - contains `warn`   → `-WARNING`
   - contains `info`   → `--INFO--`
   - contains `start`  → `-->START`
3. **no keyword matched** → parse-time error listing the accepted keywords
   (`start / done / return / warn / info / correct` — Part D), never a silent
   fallback to INFO.

Acceptance examples: `done`, `DONE`, `-DONE`, `-->DONE`, `undone` →
`DONE<---`; `returned` → `-RETURN-`; `restart` → `-->START`; `bogus` → error.
(The tool description's status text is rewritten to state the keywords —
the description is the usage channel.)

### Part D — `correction` status (annotate without removing)

**Change:** a sixth status — `correct` (contains `correct`) → a new 8-char
token `CORRECT-`, appended as a normal append-only line. It is a
clarification/addition to a previous entry; the agent names the corrected
entry in `content` (by its timestamp or a content fragment). To make precise
referencing cheap, when the status normalizes to `CORRECT-` the tool also
returns the **previous line** of the log:

```
corrects: <previous line of the log>
```

No deletion/rewriting is added anywhere (append-only stays absolute — the
maintainer confirmed the inability to correct in place is intentional).

### Prompt/doc bookkeeping (planner-applied after verification, separate commit)

`agent_readme_loop.md` §Loop log + the loop lines in the planner / worker /
looprunner role prompts: status = the keywords (start/done/return/warn/info/
correct), not the 8-char tokens; session/model optional (the tool auto-fills
from the host context); the hand-format description stays the fallback for
when the tool is not registered. Registration itself is the maintainer's
domain (live `opencode.jsonc` + per-agent grant), effective at his next
process restart.

## Acceptance

- Scratchpad smoke matrix (the loop-tool-batch Part 3 pattern, scratchpad
  context object — NOT the live loop folder):
  - Part A: context with `sessionId`/`modelId`/agent-field set → line uses
    them; each absent → arg fallback → `unknown`; the one-time context probe
    reports the live key names;
  - Part B: readback-match for a normal append; return carries
    `(created)` on first call into an empty root and `(existing)` on the
    second; a simulated mismatch path (e.g. injected pre-existing trailing
    content) surfaces `readback-MISMATCH`;
  - Part C: the normalization table — each keyword in ≥3 spellings
    (case / dash / arrow variants) → exact token; `restart` → START;
    `bogus` / empty → error naming the accepted keywords;
  - Part D: `correct` → `CORRECT-` line + `corrects: <previous line>` in the
    return; previous line is byte-correct;
  - line format unchanged: every written line byte-matches
    `<stamp> <status> <role> <session> <model> <content>`;
  - append-only: the tool never rewrites earlier lines (smoke asserts the
    file prefix is unchanged across calls).
- Full probe stays green (loop_log is smoke-based acceptance, no probe
