# Proposal — NAP size: plan state vs. session history (inbox `NAP_size.md` #1)

## Problem (measured)
- `.opencode/handover/handover_planner.md` = **963 lines / ~99k chars ≈ 25k tokens**, read in full at
  EVERY planner session start (init step 2) — a fixed ~25k-token overhead per session.
- Structure: 20 detailed per-session sections (looprun 2 → iter-14) + `Compressed archive` +
  `Standing`. Sections are 10–120 lines each, full of evidence dumps (baselines, diff scopes,
  verbatim gauges).
- WHY it is big:
  1. **Append-only, no trim rule** — a session section is added at start/close and never removed.
  2. **Dual role** — the file is both *plan state* (what a fresh session needs to resume) and
     *session audit history*; the audit half duplicates the per-iteration `plan<N>_summary.md`
     files + `loop_log.md` in the loop folders (same events, same baselines, recorded twice).
  3. **Compression exists but is not enforced** — the `Compressed archive` section (line 906)
     shows the intended end-state (one line per closed item, pointer to git/records), but only a
     few entries were ever compressed.

## Content inventory (what is in the NAP)
- Current plan state (KEEP): `Standing` section (baselines, standing items) + newest session
  section (resume context).
- History (MOVE/COMPRESS): the 19 older session sections — each already summarized in its loop
  folder `plan<N>_summary.md` and `loop_log.md`, and in git log.

## Design (independently approvable)
- **Part 1 — protocol rule (planner prompt + AGENTS.md commit routine):** at session close the
  planner compresses ITS OWN section into the `Compressed archive` list: one line
  (`<date> <iteration/direct> <one-line outcome> — details: loop folder plan<N>_summary.md + git <hash>`).
  If a session's detail exceeds what the summary file already carries, the section is APPENDED to
  `plan<N>_nap.md` in the loop folder first, then compressed. The NAP then holds only: `Standing`
  + the current session's section + the compressed list. No detailed section for a closed session
  may remain in the NAP.
- **Part 2 — one-time cleanup (worker task, ~30 min):** apply Part 1 to the 19 existing sections
  (append the over-long ones to their loop-folder files, compress in place). Expected result:
  NAP ≤ ~150 lines.
- **Part 3 — baseline hygiene:** baselines are UPDATED IN PLACE in `Standing` each session
  (never appended as new evidence lines).

## Acceptance
- `wc`-equivalent: NAP ≤ 150 lines after Part 2 (script-checked).
- A fresh planner session reads the NAP in < 5k tokens.
- Spot-check 3 compressed lines → each resolves to a loop-folder file + git hash with the detail
  present (no information lost).
